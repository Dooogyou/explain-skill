# explain

사용자가 내용을 빠르고 정확하게 이해하도록 돕는다. 짧은 답변 자체를 목표로 삼지 않는다.

## 질문에 맞추기

- 사용자의 질문과 알고 싶은 점에 바로 답한다. 지식 수준과 지정한 언어·길이·형식을 우선한다. 언어 지정이 없으면 사용자의 언어로 설명한다.
- 수준이 명시되지 않으면 질문의 맥락에 맞춰 시작한다. 필요한 정보가 없고 그 차이가 답을 바꿀 때만 묻는다. 합리적인 가정을 쓴다면 밝힌다.
- 설명을 요청하지 않은 작업에 설명 절차를 끼워 넣지 않는다. 설명과 다른 작업을 함께 요청하면 이 지침은 설명 부분에 적용한다.

## 의미를 보존하며 쓰기

- 핵심 답부터 말하고, 이해에 필요한 근거와 세부 내용을 연결한다. 모든 답을 같은 목차나 일정한 문장 수·단어 수에 맞추지 않는다.
- 쉬운 단어를 쓰고 같은 개념에는 같은 용어를 쓴다. 전문 용어가 필요하면 처음 쓰는 곳에서 독자 수준에 맞게 풀어준다. 복잡한 문장은 나누되 조건과 결론의 연결을 유지한다.
- 원문과 근거의 사실·수치·단위·비교 기준을 보존한다. 부정, 조건, 예외, 적용 범위, 인과관계, 불확실성을 생략하거나 바꾸어 결론을 더 강하게 만들지 않는다. 상관관계를 원인으로, 가능성을 보장으로 바꾸지 않는다.
- “~일 때만 …한다”는 그 조건이 아니면 …하지 않는다는 뜻이다. 조건을 만족하면 반드시 …한다는 뜻은 아니다. 예를 들어 “회원일 때만 할인된다”는 비회원은 할인되지 않는다는 뜻이지, 회원이면 반드시 할인된다는 뜻이 아니다. 핵심 문장·목록·표·비유 어디에서도 “~이면 …한다”로 바꾸지 않는다. 다른 예외를 함께 적어도 조건의 방향은 바뀌지 않는다.
- “A만 된다”, “A만 막힌다”처럼 범위를 한정하는 말은 그 밖의 것에 대한 정보도 담는다. “읽기만 허용”은 쓰기가 허용되지 않는다는 뜻이고, “주말에만 운영”은 평일에는 운영하지 않는다는 뜻이다. 원문이 이렇게 정한 범위를 “그 밖은 알 수 없음”으로 바꾸어 제한을 약하게 만들지 않는다. 원문이 정하지 않은 것만 모른다고 표시한다.
- 제공된 자료와 추론을 구분한다. 원문에 모순이나 오류가 있으면 조용히 고쳐 쓰지 말고 무엇이 불분명한지 짚는다. 확인하지 않은 사실이나 수치를 설명을 매끄럽게 하려고 채워 넣지 않는다.
- 합계·평균·1인당 값을 계산하기 전에 전체 기준인지 개인별 기준인지와 배분 조건이 주어졌는지 확인한다. 기준이 불명확하면 계산을 생략하거나 필요한 가정을 계산 전에 밝힌다. 단정한 뒤에 모른다는 말을 덧붙이는 것으로 가정을 대신하지 않는다.
- 비유나 예시는 이해를 도울 때만 쓴다. 가상의 수치·사례는 가상이라고 밝히고, 비유가 핵심 성질을 다르게 보이게 할 수 있으면 그 한계를 설명한다. 비유를 실제 작동 원리나 증거로 대신하지 않는다.
- 명료성 원칙은 STE에서 참고했지만 공식 ASD-STE100 준수나 수치로 표현한 준수율을 주장하지 않는다.

## 표현 방식 고르기

1. 사용자가 지정한 형식을 먼저 따른다. 표·그림 금지, 정확한 문장 수, JSON만 출력 같은 제약도 지킨다. 설명을 덧붙여 지정 형식을 깨뜨리지 않는다.
2. 기본은 글이다. 정의나 한 가지 질문은 글로 충분하면 그대로 답한다.
3. 여러 항목을 같은 기준으로 비교할 때는 표를 고려한다. 단위와 조건을 함께 쓰고, 비교할 정보가 없으면 모른다고 표시한다.
   조건을 표로 옮길 때는 각 칸이 원문보다 강하거나 약해지지 않게 쓴다. “~일 때만” 조건을 만족하는 칸에는 “할 수 있음(원문은 보장하지 않음)”처럼 쓰고, 조건 밖의 칸에만 “하지 않음”을 쓴다.
4. 구조·관계·흐름을 눈으로 따라가면 이해가 쉬워질 때는 작은 정적 다이어그램을 고려한다. 질문에 필요한 관계만 넣는다.
5. 이해에 충분한 표현을 골랐으면 멈춘다. 같은 내용을 글·표·그림으로 모두 반복하거나 요청하지 않은 파일을 만들지 않는다.

## 작은 정적 다이어그램

- 렌더링 지원을 알 수 없으면 텍스트 도식이나 단계 목록을 쓴다. Mermaid가 지원되는 환경이거나 사용자가 Mermaid 소스를 요청하면 단순한 Mermaid 도식을 사용할 수 있다. 별도 렌더러 설치나 외부 서비스를 필수로 삼지 않는다.
- 노드에는 일관된 이름을 붙인다. 화살표가 순서·데이터 이동·의존성 중 무엇을 뜻하는지 드러낸다. 관련 있다는 이유만으로 인과 화살표를 그리지 않는다.
- 결론에 영향을 주는 분기 조건, 예외 경로, 반복을 유지한다. 관계가 너무 많으면 질문의 범위를 좁혀 보여주거나 글·표로 바꾼다.
- 그림이 보이지 않아도 핵심을 알 수 있도록 짧은 글이나 표를 함께 제공한다. 사용자가 도식 소스만 요구했다면 그 형식을 우선하고, 소스의 노드·선 라벨에 핵심 조건이 드러나게 한다.
- 소스를 작성한 것과 실제로 렌더링해 확인한 것을 구분한다. 확인하지 않은 표시 결과를 검증했다고 말하지 않는다.

## HTML·영상 요청

인터랙티브 HTML과 영상 제작은 이 스킬 v1의 지원 범위 밖이다. 해당 요청에서는 이 한계를 짧게 알리고 사용자가 원하는 산출물을 유지한다. 현재 모델의 일반 기능이나 사용 가능한 다른 도구로 진행할 수 있으면 그 기능으로 이어간다. 이 스킬을 이유로 일반 기능을 금지하거나, 요청한 매체를 말없이 글로 대체하지 않는다. 실행할 수 없다면 가능한 글·표·정적 도식 대안을 제시한다. 그런 요청이 없는데 먼저 HTML·영상으로 확장하지 않는다.

## 보내기 전 확인

질문에 직접 답했는지, 사용자 형식을 지켰는지, 사실과 중요한 한정 조건이 남아 있는지 확인한다. “만”이나 “~일 때만”이 들어간 조건이 핵심 문장과 표에서 원문과 같은 방향과 범위로 남았는지도 확인한다. 선택한 표나 그림이 이해를 돕는지, 표시되지 않아도 핵심이 전달되는지 확인하고 불필요한 반복을 덜어낸다.
